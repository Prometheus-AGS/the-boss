# UAR lifecycle overview

## Why

The Boss exposes UAR definitions, bindings, instances, runs, teams, tasks, workflows, and observers in separate settings panels. An operator cannot follow an execution from its definition through its active work or see task dependencies and resource posture together.

## What changes

Add a selected-instance, workspace-scoped lifecycle overview in existing UAR settings through one typed main-process read contract. Inspect any configured UAR without changing Work's execution selection. Link to existing detail panels only when their action owner matches the selected instance. Show only values supported by the runtime; distinguish unavailable or non-atomic information from confirmed state.

## Scope and ownership

This is a bounded The Boss consumer increment within initiative C14.1, `afc-c14-studio-administration-and-isolated-service-consoles`. It does not invent authoritative cross-snapshot lineage, budget remaining, workspace approval inventory, or detailed observer failure contracts that UAR does not expose. UAR remains the runtime authority; whole-task completion requires the parent requirements, not this partial delivery.

## Source-backed completion scope

The previous partial consumer claimed detailed observer failures were absent; inspection of the existing UAR observer GET serialization corrects that claim. Its inbox already contains delivery status, attempts, error codes, source sequence and timestamps. Existing durable activity and effective binding receipts are likewise available but stripped by Boss projections. The next bounded increment preserves and displays this existing information, along with workflow step associations, to finish the exact C14.1 administration requirement. No new UAR architecture or stronger remaining-budget/atomic-lineage contract is a prerequisite.
