## Observed isolation defect and assigned source correction

The lead reported starting a **new launcher-isolation-only attempt against existing 2.2.38**, then promptly sending `SIGTERM` to its exact owned app PID **34119** after the shell-path finding. The receipt was incomplete; no pass or new 2.2.38 qualification is claimed. This statement is the lead's report, not a desktop-owner-observed runtime result. The desktop owner performed no app operation. Operate only new 2.2.39 after complete source/build; do not repeat this old-candidate attempt.

Read-only source reproducer: `PrometheusIntegrationService.initialize()` calls `installCommandPath()`. `commandPath.ts:shellBlocks()` resolves `application.getPath('external.shell.home')`, then `installCommandPath()` passes `.profile`, `.bashrc`, `.bash_profile`, `.zprofile`, `.zshrc` and fish startup paths to `updateShellRcFile()`. Before repair, the registry selected the real `sysHome` even when `PRIVATE_PROFILE_PATHS` was active. `THE_BOSS_PROFILE_ROOT` therefore isolated userData/commands but not these startup-file writes.

Assigned correction touches only `src/main/core/paths/constants.ts` and `pathRegistry.ts`: add typed `home: <privateRoot>/home`, create it alongside the existing private directories, and select it for `external.shell.home` before the existing dev/default branches. The ordinary/dev paths and `HOME` remain unchanged. This is security isolation at the actual user shell-file write boundary; no new daemon, preference or public IPC is added. No test/check/compiler/build/app operation followed this source correction.

Read-only backup forensics then confirmed that only `.profile`, `.bashrc` and `.bash_profile` changed, each exactly equal to the verified original backup with this attempt's generated managed block substituted; all bytes outside managed blocks were unchanged. On explicit lead authorization those three were restored under the existing per-file lock after rechecking the exact transform, preserving mode 0600 and retaining current bytes in a private 0700 forensic directory for rollback. [The sanitized receipt](incomplete-launcher-rc-restoration.json) records hashes and paths without contents. `.zprofile`, `.zshrc` and the fish registration file were untouched by this restoration and contained no command path from the incomplete attempt.

Graph limitation: `.compass/{verification.json,config.toml}` were absent. Bounded `search_symbols` and depth-1 `get_impact` for `resolvePrivateProfilePaths` returned `no_match` with incomplete coverage; an initial 2,000-byte response cap was too small and was increased to 4,000. Source search and the existing path/module architecture were used; graph absence was not treated as proof of no callers. [desktop-source-inventory.json](desktop-source-inventory.json) records the exact repaired bytes and trace sources.

The operation wrapper now requests `keep-open` for both phases, verifies the launched app PID, exact executable and private-profile command, then signals **that PID only** with `SIGTERM` and waits eight seconds. It records an unresolved stop and does not reopen or escalate if the process remains. The maintained launcher must honor keep-open on failed scenarios as well; setting retention only after scenario success still enters its forced cleanup path on a failure, so the wrapper refuses that older launcher source before launch.
